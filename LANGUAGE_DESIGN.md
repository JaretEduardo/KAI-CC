# KAI Language Design

> Status: Draft  
> Target version: KAI 0.1

## 1. Overview

KAI is an AI-native compiled systems programming language designed for software that is efficient to generate, inspect, debug, and maintain by both humans and AI coding agents.

KAI aims to combine:

- compact and predictable source code
- static type safety
- native performance
- transparent memory behavior
- deterministic tooling
- structured compiler diagnostics
- semantic introspection
- low context and token overhead for AI agents

KAI is not designed to minimize characters at the cost of readability.

Instead, KAI attempts to minimize the amount of information that humans and AI agents must process in order to understand and safely modify a program.

---

## 2. Motivation

Modern AI coding agents frequently work with languages and ecosystems that were designed exclusively for human developers.

This creates several inefficiencies:

- large amounts of source code must be read to understand a project
- compiler errors are often verbose or unstructured
- dependency relationships are not always directly queryable
- multiple equivalent language constructs increase ambiguity
- implicit behavior makes automated reasoning harder
- code generation can require excessive boilerplate
- refactoring may require scanning large portions of a codebase

KAI explores what a systems programming language could look like if AI-assisted software development were considered from the beginning.

The compiler should not only translate source code into native programs.

It should also act as a semantic engine capable of explaining the program to development tools and AI agents.

## 3. Design Principles

### 3.1 Predictability

KAI should prefer one clear and canonical way to express common operations.

The language should avoid unnecessary syntax variants and hidden behavior.

### 3.2 Token Efficiency

KAI source code should remain compact without becoming cryptic.

Token efficiency should come from:

- concise syntax
- type inference
- minimal boilerplate
- strong module boundaries
- compiler-provided semantic information
- structured tooling

Token efficiency must be measured rather than assumed.

Future benchmarks should compare equivalent programs written in KAI and other languages using multiple model tokenizers.

### 3.3 Static Safety

KAI should catch as many programming errors as reasonably possible during compilation.

The initial language will use static typing.

Implicit conversions should be limited and predictable.

### 3.4 Native Performance

KAI is a compiled language.

Programs should compile to native machine code without requiring a virtual machine.

The reference compiler will initially target LLVM.

### 3.5 Transparent Behavior

Developers should be able to inspect what the compiler is doing.

KAI tooling should eventually expose:

- inferred types
- symbol references
- dependency relationships
- generated IR
- generated assembly
- memory information
- optimization information

### 3.6 AI-First Diagnostics

Compiler diagnostics should be useful to both humans and machines.

Each diagnostic should have:

- stable diagnostic code
- source location
- concise description
- relevant types or values
- machine-readable representation

Example:

    E0102
    src/main.kai:12:8

    expected: i32
    found: str

Structured output should eventually be available through:

    kai check --json

### 3.7 Maintainability

KAI should favor long-term readability over cleverness.

Code generated by an AI agent should still be understandable and maintainable by a human developer.

### 3.8 Systems-Level Capability

KAI should eventually allow low-level programming when required.

The language should not hide the underlying machine completely.

Future versions may expose:

- pointers
- explicit memory regions
- SIMD
- native calling conventions
- hardware-specific operations

These capabilities should not complicate ordinary KAI programs.

## 4. Memory Philosophy

KAI will not require a tracing garbage collector.

The long-term goal is deterministic resource management.

The exact ownership and borrowing model is not yet finalized.

Current direction:

- values have clear ownership
- resources are released deterministically
- scope-based cleanup is preferred
- explicit low-level operations may require `unsafe`
- ordinary programs should not require manual `alloc` / `free`

Example direction:

    fn process() {
        let data = Buffer<f32>(1024)
        compute(data)
    }

`data` should be automatically cleaned up when its lifetime ends.

The memory model will be designed incrementally and must remain simpler than Rust's full borrow-checking model unless stronger complexity is justified.

## 5. AI Semantic Tooling

KAI-CC should eventually expose its semantic knowledge through tooling.

Possible commands include:

    kai inspect User
    kai type expression
    kai refs calculate_total
    kai deps authenticate
    kai impact User.id

The compiler should be able to provide information without requiring an agent to manually read every relevant source file.

Example:

    $ kai impact User.id

    symbol: User.id

    defined:
      src/user.kai:8

    referenced:
      12 locations

    changing this symbol may affect:
      5 functions
      2 public APIs
      4 tests

Machine-readable equivalents should also be available.

---

## 6. Language Philosophy

KAI should be:

- statically typed
- compiled
- readable
- explicit when behavior matters
- concise when information can be inferred safely
- deterministic
- tooling-friendly
- suitable for systems programming
- suitable for large codebases

KAI should not become a collection of unrelated convenience features.

Every major language feature must justify its complexity.

---

## 7. Non-Goals for KAI 0.1

KAI 0.1 will NOT attempt to provide:

- classes
- inheritance
- async/await
- macros
- compile-time metaprogramming
- GPU programming
- automatic parallelization
- package registry
- web frameworks
- JIT compilation
- garbage collection
- self-hosting
- multiple code generation backends
- advanced borrow checking

These features may be explored in later versions.

---

## 8. Long-Term Goals

Potential long-term goals include:

- generics
- traits
- package management
- semantic agent API
- SIMD
- parallel programming
- GPU computing
- WebAssembly
- cross compilation
- self-hosted compiler
- compiler plugins
- rich profiling and debugging tools

These are directions, not commitments.

---

## 9. Self-Hosting

The first implementation of KAI-CC will be written in C++.

Once KAI is expressive and stable enough to implement its own compiler, a self-hosted compiler may be developed.

Possible bootstrap process:

    KAI-CC Stage 0
    C++ implementation
          |
          v
    compiles KAI compiler source
          |
          v
    KAI-CC Stage 1
    written in KAI
          |
          v
    compiles itself
          |
          v
    KAI-CC Stage 2

Self-hosting is a long-term milestone and must not influence KAI 0.1 development at the cost of simplicity.

---

## 10. Core Rule

KAI should not try to make AI agents better programmers through prompting.

KAI should reduce the number of opportunities an AI agent has to make incorrect changes through language design, static analysis, structured diagnostics, and semantic tooling.
