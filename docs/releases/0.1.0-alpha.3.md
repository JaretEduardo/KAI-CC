# KAI v0.1.0-alpha.3

**Status: alpha / experimental / pre-release.** Syntax, semantics, and
tooling may change significantly without notice. There are no stability
guarantees on CLI flags, exit codes, or the semantic-tooling JSON schema
between pre-release versions. **Do not use KAI for production software.**

## Highlights

This is a **language-feature release**: six merged milestones on top of
alpha.2's platform-support baseline (Linux + Windows x86_64), all
native-executable-verified, none of them changing compiler architecture, CI
gating, or platform support.

- Executable half-open integer range `for` loops (M6).
- Fixed-size arrays `[T; N]` with checked compile-time and runtime bounds,
  whole-array value semantics, and array function parameters/returns
  lowered as a direct LLVM aggregate (M7-M8).
- General nested fixed-array indexing at any depth (M9).
- Immutable, non-owning slice values `[T]` (M10).
- A restricted, flow-sensitive slice provenance analysis that makes a
  narrow, provably-safe class of slice returns executable (M11).
- Community-readiness work: `CONTRIBUTING.md`, issue templates, a stale
  platform-support claim fixed in `COMPILER_ARCHITECTURE.md`, and a clearer
  newcomer path in `README.md`.

## Supported platforms

- **Linux x86_64**
- **Windows x86_64**

Unchanged from alpha.2. No macOS, ARM64 (any OS), or Windows-on-ARM binary
packages exist or are claimed. No stable ABI/API is claimed between
pre-release versions.

## Installation - Linux

Download `kai-0.1.0-alpha.3-linux-x86_64.tar.gz` from the
[GitHub Releases page](https://github.com/JaretEduardo/KAI-CC/releases) and
extract it anywhere - no root required, no install into a system location.
**End users do not need LLVM installed**; `kaicc` statically links the LLVM
components it needs. Native compilation still requires a working host C
toolchain: a `cc`/`clang`/`gcc`-compatible compiler driver on `PATH`, plus
the platform's normal libc development/startup files and linker support
(e.g. a minimal Ubuntu 22.04 install needs both `gcc` and `libc6-dev`). See
the root [`README.md`](../../README.md)'s Linux quickstart for the full
copy-pasteable walkthrough.

## Installation - Windows

Download `kai-0.1.0-alpha.3-windows-x86_64.zip` from the
[GitHub Releases page](https://github.com/JaretEduardo/KAI-CC/releases) and
extract it anywhere - this works even from a path containing spaces (e.g.
under `C:\Users\Jane Doe\Downloads\`). Install a host C toolchain - only
needed to *compile* KAI programs, not to run `kaicc.exe` itself
(`--version`, `--help`, and the semantic-tooling commands all work with no
toolchain installed at all). The one route this project tests is
[WinLibs GCC](https://github.com/brechtsanders/winlibs_mingw), extracted to
a directory whose path does **not** contain spaces (a confirmed limitation
of that specific toolchain distribution, not of KAI). See the root
[`README.md`](../../README.md)'s Windows quickstart for the full
walkthrough, including the exact `no usable host C compiler driver found`
error (exit code 9) you'll see if the toolchain step is skipped.

## VS Code extension

`editors/vscode` (v0.7.0, bumped from v0.6.0 to distinguish this release's
newer bundled compiler) provides syntax highlighting, snippets, basic
completion, KAI file icons, and Build/Run Current File commands. No
extension functionality changed in this release - the version bump is
packaging-only. Distributed as two separate, platform-specific packages:

- `kai-language-linux-x64-0.7.0.vsix`
- `kai-language-win32-x64-0.7.0.vsix`

Each bundles that platform's native `kaicc`/`kaicc.exe` and runtime by
default (`kai.compilerPath` remains available as an explicit override). On
Windows, Run Current File produces and executes a native `.exe`. Compiling
KAI programs from the extension still requires the same host C toolchain
described above, on either platform. See
[`editors/vscode/README.md`](../../editors/vscode/README.md) for full
extension documentation.

## Compiler capabilities

Unchanged from alpha.2 plus everything below in "New in alpha.3": primitive
integer types, `f32`/`f64`, `bool`, `char`, the unit type, `let`/`mut`
bindings, arithmetic/comparison/short-circuit-logical expressions, function
parameters/calls/recursion, `if`/`else if`/`else`, `while`, explicit
`return`, and `str` literals/parameters/returns with `print(str)`.

## New in alpha.3

### For loops

`for i in start..end` over a half-open integer range is real, native,
executable code (M6): both endpoints are evaluated exactly once, the loop
variable is immutable, and both signed and unsigned integer ranges are
supported. KAI 0.1 still has no general iteration protocol - `for x in
someCollection` over anything other than a literal integer range remains a
semantic error, not silently ignored.

### Arrays

A fixed-size array `[T; N]` is real, native, executable code (M7-M8):
literal creation, checked indexed reads/writes (a compile-time-constant
out-of-bounds index is a compile error; a dynamic one traps at runtime),
zero-length arrays, and `for`-range integration. Arrays are KAI value
types: whole-array initialization/assignment/self-assignment are ordinary
value copies with no aliasing, and array function parameters/returns are
lowered as a direct LLVM aggregate `[N x T]` argument/result - never
`sret`/`byval`/a hidden pointer, and no promised stable external C ABI.
General nested indexing (M9) - `matrix[i][j]`, and deeper - independently
bounds-checks each level before computing that level's own element address;
mutation through a nested chain is allowed exactly when the root binding is
a mutable local, and an array-valued intermediate index result is an
ordinary independent copy, never an alias.

### Slices

`[T]` is a real semantic `TypeKind::Slice` type (M10), structurally
distinct from a fixed array (`[i32]` and `[i32; 3]` are never
interchangeable). Executable: the explicit `slice(array)` builtin (never an
implicit array-to-slice conversion), `len(array | slice | str) -> u64`,
local slice storage/copy/rebinding, checked indexed reads (the same
`llvm.trap`-guarded runtime bounds model arrays use), and a slice function
parameter (copy of the view, by value). Slice indexed writes remain
unconditionally rejected.

### Restricted Slice lifetime/provenance behavior

M11 adds a flow-sensitive provenance analysis (`External`/`Local`/
`Unknown`, tracked per binding, never part of the Slice type itself) that
proves a narrow, sound class of slice returns safe and makes exactly that
class executable. **This is explicitly not a general borrow checker** -
there is no interprocedural provenance inference, no mutable slices, no
composite/array-wrapped slice provenance, and no general lifetime syntax.

Safe and executable - relaying a parameter's own slice straight back out:

```kai
fn id(xs: [i32]) -> [i32] {
    return xs
}
```

Only the view itself (a pointer and a length) is transported back to the
caller, never a copy of the viewed elements - and never a dangling pointer,
since the returned pointer is never rebased away from storage the caller
already owns.

Rejected - the array is local to the function, so its storage does not
outlive the call:

```kai
fn bad() -> [i32] {
    let a = [1, 2, 3]
    return slice(a)
}
```

This fails with a dedicated `EscapingLocalSlice` diagnostic, not a generic
type error. Re-forwarding an `Unknown`-provenance slice-returning call
result is *also* rejected, even though it might be safe in a specific case
- interprocedural provenance inference does not exist yet, so any call
result is conservatively treated as unprovable rather than analyzed further.
Using an `Unknown`-provenance value locally (not returning it) remains
completely valid; the restriction is specifically about what may escape a
function via `return`.

## Semantic tooling

`kaicc inspect`/`definition`/`references`/`callers`/`callees`/`call-graph`
remain fully available on both platforms, with no host C toolchain
required - see [`docs/CLI.md`](../CLI.md). Slice/array provenance and other
new M6-M11 internal analyses have no public query surface and are not
exposed through any of these commands.

## Examples

The curated release examples (compiled AND run against the packaged
`kaicc`, exact stdout asserted before packaging) now include, alongside the
existing `hello`/`functions`/`conditions`/`variables` set:

- `loops.kai` - `while`, then a `for` loop over an integer literal range
- `fibonacci.kai` - recursion plus a `for`-range loop
- `arrays.kai` - fixed-size arrays: literal creation, checked indexed
  reads/writes, array function parameters/returns, nested indexing
- `slices.kai` - `slice(array)`, `len()`, a slice function parameter, and
  an executable safe slice return

See [`examples/README.md`](../../examples/README.md) for the exact status
of every tracked example, including diagnostic and design/future ones that
are intentionally not packaged.

## Known limitations

Parses and/or type-checks in some form, but explicitly **not**
backend-lowerable yet:

- an array that recursively contains a slice as a function
  parameter/return/local type, and sub-slicing/slice-of-slice
- mutable slices, and writable slice indexing
- interprocedural slice-provenance inference (a call result's provenance is
  always `Unknown`; re-forwarding an `Unknown` slice-returning call result
  as a return value remains rejected)
- general references (`&T`) and a general borrow checker/lifetime syntax -
  M11's provenance analysis is a narrow, restricted safety check, not a
  general ownership/lifetime system
- general iteration (`for x in someArray`), inclusive/reverse ranges, step
  syntax, `break`/`continue`, and a first-class `Range` value
- structs, enums, generics, traits
- `Result`/`Option`, and advanced ownership/borrowing beyond the above
- an owned, dynamic `String` type (`str` today is a `Copy`, immutable,
  non-owning view only)
- string concatenation, equality, slicing, and indexing
- modules/packages

Additionally: complete UTF-8 **validation** is not yet implemented (`str`
preserves whatever bytes the source file contained, without validating
well-formedness); no Language Server Protocol support and no semantic
editor features beyond the VS Code extension's existing syntax
highlighting/basic completion; no macOS or ARM64 (any OS) binary packages;
no stable ABI is claimed for any lowered aggregate (array or slice).
