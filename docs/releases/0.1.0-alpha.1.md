# KAI v0.1.0-alpha.1

**Status: alpha / pre-release.** This is the first published pre-release of
the KAI reference compiler (`kaicc`). Syntax, semantics, and tooling may
change significantly without notice. **Do not use KAI for production
software.**

**Platform:** Linux x86_64 only. No Windows or macOS support exists or is
claimed. The portable binary release is built and tested against an
**Ubuntu 22.04** baseline, with a verified forward smoke test on a current
Fedora host - this is not a claim of universal Linux compatibility, only
what has actually been verified.

## What's in this release

**Compiler pipeline:** a complete, working, end-to-end pipeline - Lexer ->
Parser/AST -> SemanticAnalyzer -> TypeChecker -> ControlFlowAnalyzer ->
LLVM IR -> native object emission -> native linking -> a real executable -
invoked with one command, `kaicc <file.kai> -o <output>`.

**Language features implemented:** primitive integer types
(`i8`/`i16`/`i32`/`i64`/`u8`/`u16`/`u32`/`u64`), `f32`/`f64`, `bool`,
`char`, the unit type `()`; arithmetic, comparison, and short-circuit
logical (`&&`/`||`) expressions; `let`/`mut` bindings and assignment;
function parameters, calls, forward calls, and recursion;
`if`/`else if`/`else`; `while`; explicit `return`.

**`str` support:** string literals, explicit `str` local annotations, and
`str` function parameters and return types, with `print(str)`. `str` is a
`Copy`, immutable, non-owning text view; an owned `String` type remains
unimplemented (see "Known limitations" below).

**Native executable generation:** `kaicc` emits a real native object file
and links it (via the host's own `cc`/`clang`/`gcc` driver) into a
directly runnable executable - not an interpreter and not a bytecode VM.

**Semantic/AI-native tooling:** `kaicc` exposes its own compiler-resolved
semantic model directly - `inspect`, `definition`, `references`,
`callers`, `callees`, and `call-graph` - so a tool or an AI agent can query
symbol/type/call relationships without reconstructing them from text
search. See [`docs/CLI.md`](../CLI.md).

**VS Code support:** the `editors/vscode` extension (v0.5.0) provides
syntax highlighting, snippets, basic completion, KAI file icons, and
Build/Run Current File commands, with a bundled Linux x86_64 `kaicc` and
runtime when packaged as a VSIX.

**Portable artifact behavior:** the portable release tarball statically
links the LLVM components `kaicc` needs - **end users do not need LLVM
installed**. A bundled `libz3.so.4` (an upstream LLVM packaging dependency
KAI-CC itself never calls into) is the only extra runtime shared library.
Native compilation still requires a working host C toolchain: a
`cc`/`clang`/`gcc`-compatible compiler driver on `PATH`, since `kaicc`
shells out to it for the final native link step of every program it
compiles, **plus** the platform's normal libc development/startup files
and linker support - a bare compiler driver package is not always
sufficient by itself (confirmed on a minimal Ubuntu 22.04 install, where
`gcc` alone failed to link until `libc6-dev` was also installed).

## Known limitations

Parses and/or type-checks in some form, but explicitly **not**
backend-lowerable yet:

- `for` loops (LLVM code generation is not implemented)
- arrays/slices as function parameter, return, or local types
- structs, enums, generics, traits
- `Result`, general references (`&T`), and advanced ownership/borrowing
- an owned, dynamic `String` type
- string concatenation, equality, slicing, and indexing
- modules/packages

Additionally, complete UTF-8 **validation** is not yet implemented: `str`
values are preserved byte-for-byte end to end (including an embedded
`\0` byte, which is itself valid UTF-8), but the compiler does not
currently validate that `str` contents are well-formed UTF-8 - it
preserves whatever bytes the source file contained.
