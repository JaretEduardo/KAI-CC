# KAI v0.1.0-alpha.2

**Status: alpha / experimental / pre-release.** Syntax, semantics, and
tooling may change significantly without notice. There are no stability
guarantees on CLI flags, exit codes, or the semantic-tooling JSON schema
between pre-release versions. **Do not use KAI for production software.**

## Highlights

- **Native Windows x86_64 compiler support**, alongside the existing
  Linux x86_64 support - the same source tree builds `kaicc.exe`, runs
  its full CTest suite, and compiles/links real `.kai` programs into
  native `.exe` executables.
- **Deterministic, byte-identical `print` output** on both platforms:
  every line is terminated with exactly one LF (`0x0A`) byte, never a
  host-native CRLF, even on Windows.
- **A portable Windows x86_64 `.zip` distribution**, analogous to the
  existing Linux tarball, with an audited, minimal bundled-DLL closure
  and matching third-party license/notice coverage.
- **A platform-specific Windows x64 VS Code extension package**, in
  addition to the existing Linux x64 package, with Build/Run Current
  File support producing native Windows executables.
- **An independent "fresh user" release gate**: an automated CI job
  proves an ordinary Windows user - with none of KAI's own MSYS2/LLVM/
  CMake/Ninja build toolchain installed, only a separately-downloaded
  host C toolchain - can download the released ZIP and VSIX and
  compile/run real KAI programs end to end.

## Supported platforms

- **Linux x86_64**
- **Windows x86_64**

No macOS, ARM64 (any OS), or Windows-on-ARM binary packages exist or are
claimed. No stable ABI/API is claimed between pre-release versions.

## Windows installation

Once `v0.1.0-alpha.2` release artifacts are published:

1. Download and extract `kai-0.1.0-alpha.2-windows-x86_64.zip` anywhere -
   this works even from a path containing spaces (e.g. under
   `C:\Users\Jane Doe\Downloads\`).
2. Install a host C toolchain - only needed to *compile* KAI programs,
   not to run `kaicc.exe` itself (`--version`, `--help`, and the
   semantic-tooling commands all work with no toolchain installed at
   all). The one route this project tests is
   [WinLibs GCC](https://github.com/brechtsanders/winlibs_mingw) (a
   standalone, installer-free `.zip` build of GCC/MinGW-w64): download
   the UCRT runtime, `x86_64`, `.zip` variant, and **extract it to a
   directory whose path does not contain spaces** (e.g.
   `C:\Tools\winlibs`) - this is a confirmed limitation of that specific
   toolchain distribution, not of KAI. Add the extracted `mingw64\bin`
   folder to your `PATH`, or set `KAI_CC` to the full path of `gcc.exe`
   inside it (see [`docs/CLI.md`](../CLI.md)).
3. `kaicc.exe --version`, `.\bin\kaicc.exe .\examples\hello.kai -o hello`,
   `.\hello.exe` - see the root [`README.md`](../../README.md)'s Windows
   quickstart for the full walkthrough.

If step 2 is skipped, compiling a program fails with a clear
`no usable host C compiler driver found` error (exit code 9) rather than
a confusing crash or DLL error.

## Linux installation

Once `v0.1.0-alpha.2` release artifacts are published, download and
extract `kai-0.1.0-alpha.2-linux-x86_64.tar.gz` - **end users do not need
LLVM installed**; `kaicc` statically links the LLVM components it needs.
Native compilation still requires a working host C toolchain: a
`cc`/`clang`/`gcc`-compatible compiler driver on `PATH`, plus the
platform's normal libc development/startup files and linker support (a
bare compiler driver package is not always sufficient by itself - e.g. a
minimal Ubuntu 22.04 install needs both `gcc` and `libc6-dev`).

## VS Code extension

`editors/vscode` (v0.6.0) provides syntax highlighting, snippets, basic
completion, KAI file icons, and Build/Run Current File commands. It is
distributed as two separate, platform-specific packages - install the
one matching your platform:

- `kai-language-linux-x64-0.6.0.vsix`
- `kai-language-win32-x64-0.6.0.vsix`

Each bundles that platform's native `kaicc`/`kaicc.exe` and runtime by
default (`kai.compilerPath` remains available as an explicit override).
On Windows, Run Current File produces and executes a native `.exe`.
Compiling KAI programs from the extension still requires the same host C
toolchain described above, on either platform. See
[`editors/vscode/README.md`](../../editors/vscode/README.md) for full
extension documentation.

## Compiler/language capabilities

Unchanged from alpha.1 - this release is a platform-support and
packaging milestone, not a language-feature release. A complete,
working, end-to-end pipeline (lexer, parser, semantic analysis, type
checking, control-flow analysis, LLVM codegen, native object emission
and linking) compiles a real subset of KAI source - primitive integer
types, `f32`/`f64`, `bool`, `char`, the unit type, `let`/`mut` bindings,
arithmetic/comparison/short-circuit-logical expressions, function
parameters/calls/recursion, `if`/`else if`/`else`, `while`, explicit
`return`, and `str` literals/parameters/returns with `print(str)` - into
a real native executable, identically on Linux and Windows.

## Semantic tooling

`kaicc inspect`/`definition`/`references`/`callers`/`callees`/
`call-graph` remain fully available on both platforms, with no host C
toolchain required - see [`docs/CLI.md`](../CLI.md).

## Portability/toolchain requirements

| | Linux x86_64 | Windows x86_64 |
| --- | --- | --- |
| Run `kaicc`, `--version`/`--help`, semantic tooling | No extra toolchain needed | No extra toolchain needed |
| Compile/link a `.kai` program | `cc`/`clang`/`gcc`-compatible driver + libc dev/startup files on `PATH` | `clang`/`gcc`-compatible driver on `PATH` (tested route: WinLibs GCC, extracted to a space-free path) |
| KAI's own install/source/output paths | May contain spaces | May contain spaces |

## Known limitations

Parses and/or type-checks in some form, but explicitly **not**
backend-lowerable yet:

- `for` loops (LLVM code generation is not implemented)
- arrays/slices as function parameter, return, or local types
- structs, enums, generics, traits
- `Result`, general references (`&T`), and advanced ownership/borrowing
- an owned, dynamic `String` type (`str` today is a `Copy`, immutable,
  non-owning view only)
- string concatenation, equality, slicing, and indexing
- modules/packages

Additionally: complete UTF-8 **validation** is not yet implemented (`str`
preserves whatever bytes the source file contained, without validating
well-formedness); no Language Server Protocol support; no macOS or
ARM64 (any OS) binary packages.

The AI-native semantic-benchmark infrastructure exists in this
repository, but formal trial counts remain zero (textual: 0, semantic:
0) - no benchmark results are claimed in this release.
